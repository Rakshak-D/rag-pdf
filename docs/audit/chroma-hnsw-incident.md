# Chroma HNSW reader incident

**Status as of 2026-10-28: unresolved.** The error has occurred in this repository, but no failure-time snapshot has connected it to one specific on-disk state or cache lifecycle. No runtime or dependency change is justified by the evidence so far.

## Incident summary

The two affected paths are:

- `tests/integration/test_chroma_store.py::test_supplied_vectors_are_persistent_and_modalities_are_separate`
- `tests/integration/test_retrieval.py::test_combined_retrieval_validates_report_and_keeps_modalities_separate`

The observed Chroma error is `InternalError: Error creating hnsw segment reader: Nothing found on disk`. The first path surfaces it as `ChromaStoreInputError`; the second surfaces it as `RetrievalQueryError` through the retrieval wrapper. The failure occurs at the Chroma collection query boundary (`ChromaVectorStore.query_text()` → `_query()` → `collection.query()`).

The observed environment is CPython 3.10.11, 64-bit Windows, Chroma 1.5.0, installed from the repository's `rag-env`. The installed `RustBindingsAPI` reports `hnsw_cache_size=102`. Its Python source derives that value as the Windows CRT file-handle limit (512 in this environment) divided by five, then passes it into the Rust bindings. This is an implementation-derived value, not a supported `PersistentClient` option. The installed client exposes neither a public `close()` method nor a context-manager API; the project's `ChromaVectorStore.close()` drops its wrapper references.

## Test evidence

Both named tests have failed at least once in earlier runs and passed on isolated reruns. The retained history does not provide a reliable total-attempt denominator for those older failures, so no failure rate is claimed.

The three latest full-suite runs with the opt-in diagnostic plugin each completed with **584 passed, 7 skipped**. Neither HNSW error recurred, and the plugin captured no failure snapshot. Earlier instrumented target and combined runs also passed without a snapshot. These successful runs do not establish that the problem is fixed.

The diagnostic plugin is opt-in and restricts inspection to verified temporary test stores. It records a bounded inventory and pickle structure only after the wrapped query exception reaches the adapter wrapper. Therefore no actual failing-test snapshot is currently available. The separate synthetic cache-size-one probe also passed and did not directly observe an eviction event.

The error path in both 1.5.0 and 1.5.9 is specific: `LocalHnswSegmentReaderError::UninitializedSegment` formats as “Nothing found on disk”; `LocalSegmentManagerError` prefixes “Error creating hnsw segment reader”. Thus the message can mean an absent segment directory, absent `index_metadata.pickle`, or an empty `id_to_label` mapping. By contrast, a present but unreadable pickle and a nonempty mapping whose native index fails to load take distinct error variants. Seeing native HNSW files in a post-failure inventory alone would not rule out the metadata branches.

Current `main` additionally checks the SQLite sequence when the metadata file is missing and validates the persisted checkpoint and native files. That newer source does not retroactively establish which condition existed in the 1.5.0 test failures.

## Upstream report and relevance

[Chroma issue #7946](https://github.com/chroma-core/chroma/issues/7946) remains open as of this investigation. It reports the same reader error on Chroma 1.5.9, Python 3.11.17, Linux x86-64 under QEMU on Apple Silicon, with an explicitly forced cache size of one. The report describes an intermittent failure after adding a second collection, while querying the first. Its latest discussion (2026-10-27) points out that missing or empty `index_metadata.pickle` state can also yield this message and notes that current `main` has additional checks and live-index reuse. The reporter's later reproductions did not recur consistently. This is a useful lead, not a matching reproduction: this repository runs Chroma 1.5.0 on native 64-bit Windows with observed cache value 102, and its actual failures lack corresponding snapshots.

The project store creates a `PersistentClient` under a plan-owned temporary/persistent index path, maintains separate text and image collections with cosine distance, and delegates vector queries through `collection.query()`. The two affected tests use synthetic temporary indexes; no evidence shows they force eviction or launch concurrent work against the same segment. The plugin and synthetic harness have not observed eviction in this environment.

## Assessment and evidence needed

**Diagnosis: supported but unconfirmed.** Upstream source changes make cache eviction, concurrent cache misses, native index lifetime, and file-handle lifecycle credible areas to investigate. The exact message also has several on-disk initialization causes. None is established for this repository.

No project code or dependency change is warranted now. Revisit if a failing run captures, for the actual temporary segment, the metadata pickle presence and structural count, native-file inventory, SQLite sequence state, operation order, and cache observation. To attribute the incident to eviction, also obtain direct evidence that the relevant cache entry was evicted before the failing query (or reproduce the same failure deterministically against this installed build). A post-exception snapshot must continue to be treated as post-failure evidence, not as the exact transient state at the throw.

### Test-only instrumentation and fixed diagnostic matrix

The opt-in pytest diagnostic plugin now records bounded monotonic checkpoints around store open, upserts, close, `open_existing()`, collection counts, and each query. It records process/thread IDs, a short fingerprint prefix, reservation-marker presence, an in-process lease-object snapshot that distinguishes the current owner thread from an owner-unobserved marker, cached-system observations, and bounded file metadata only when the store is proven under that test's `tmp_path`. The marker-only state is explicitly classified as active-versus-stale unknown; the plugin does not inspect owner-token contents or claim stale-lock status. On the known exception it writes the original traceback and immediate post-exception evidence before retrieval's `finally` closes the wrapper. It does not inspect SQLite while the client is live, deserialize the installed Rust-backed fixture's pickle, alter cache settings, or replace the exception. The F smoke child records equivalent query-boundary diagnostics in its temporary failure JSON. No production code changed.

These hooks add work at each checkpoint: they read unsupported Chroma cache/lease internals and make a bounded directory traversal for file stats. That observer effect can perturb scheduling and reduce the chance of an intermittent timing-sensitive failure. Cache observations are point-in-time samples, not a complete cache history; the instrumentation does not observe eviction between checkpoints. The original runs remain the failure evidence if instrumented runs pass.

### Root-cause assessment and next gate

**Classification: Intermittent incident confirmed; controlled reproduction not established; root cause unresolved. Phase 6.12F remains blocked.** The original full-suite integration failure and the original Phase 6.12F standalone failure are preserved. The bounded diagnostic trials did not reproduce the error; that does not supersede the original failures. The Phase 6.12F recurrence demonstrates that same-process wrapper close/reopen is not a necessary condition for the error: its builder child exited before the first retrieval in the evaluation child. The full-suite test contains a same-process close/reopen and repeated-query sequence, but its retained output does not say which invocation failed. The common confirmed operation is a text collection query; that shared boundary does not establish a shared underlying cause.

The post-failure HNSW files being present does not exclude a transient segment-initialization state. No cache eviction, concurrent same-path open, missing active segment directory, SQLite sequence mismatch, or HNSW metadata-map state was observed at the instant either original exception was thrown. The successful same-process run shows that cached-system reuse can work under one trial; it does not prove cache reuse is always safe. The cold-process and evaluation-sequence successes likewise do not establish that a process boundary prevents the failure. Upstream issue #7946 remains a related lead under a different Chroma version, OS, architecture, and cache setting; matching text is not proof of matching cause. The pinned 1.5.0 Rust-backed path is the relevant local implementation, and no dependency or cache setting was changed.

No workaround or production correction is proposed. Root cause remains unknown and no deterministic reproducer was established in this bounded matrix. A later investigation should be separately scoped to capture a failure-time segment identity and correlate it with Chroma's SQLite segment metadata and the installed 1.5.0 Rust reader's initialization conditions, using only a disposable synthetic store and preserving evidence before cleanup. Do not clear Chroma caches, repair files, retry queries, or remove reservations as part of diagnosis. No release acceptance policy was approved; Phase 6.12F remains a release blocker under the current gate.
