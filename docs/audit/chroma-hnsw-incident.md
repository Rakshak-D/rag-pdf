# Chroma HNSW reader incident

**Latest status as of 2026-11-01:** one controlled uninstrumented reproduction is preserved; the subsequent eight-attempt minimal-observer matrix did not reproduce it. Root cause remains unknown and Phase 6.12F remains blocked. The earlier status paragraphs remain historical records of evidence available at those checkpoints.

**Status as of 2026-10-28: unresolved.** The error has occurred in this repository, but no failure-time snapshot has connected it to one specific on-disk state or cache lifecycle. No runtime or dependency change is justified by the evidence so far.

## Incident summary

The two affected paths are:

- `tests/integration/test_chroma_store.py::test_supplied_vectors_are_persistent_and_modalities_are_separate`
- `tests/integration/test_retrieval.py::test_combined_retrieval_validates_report_and_keeps_modalities_separate`

The observed Chroma error is `InternalError: Error creating hnsw segment reader: Nothing found on disk`. The first path surfaces it as `ChromaStoreInputError`; the second surfaces it as `RetrievalQueryError` through the retrieval wrapper. The failure occurs at the Chroma collection query boundary (`ChromaVectorStore.query_text()` → `_query()` → `collection.query()`).

The observed environment is CPython 3.10.11, 64-bit Windows, Chroma 1.5.0, installed from the repository's `rag-env`. The installed `RustBindingsAPI` reports `hnsw_cache_size=102`. Its Python source derives that value as the Windows CRT file-handle limit (512 in this environment) divided by five, then passes it into the Rust bindings. This is an implementation-derived value, not a supported `PersistentClient` option. The installed client exposes neither a public `close()` method nor a context-manager API; the project's `ChromaVectorStore.close()` drops its wrapper references.

## Test evidence

Both named tests have failed at least once in earlier runs and passed on isolated reruns. The retained history does not provide a reliable total-attempt denominator for those older failures, so no failure rate is claimed.

The three latest full-suite runs with the opt-in diagnostic plugin each completed with **584 passed, 7 skipped**. Neither HNSW error recurred, and the plugin captured no failure snapshot. Earlier instrumented target and combined runs also passed without a snapshot. These successful runs do not establish that the problem is fixed.

The diagnostic plugin is opt-in and restricts inspection to verified temporary test stores. It records a bounded inventory and pickle structure only after the wrapped query exception reaches the adapter wrapper. Therefore no actual failing-test snapshot is currently available. The separate synthetic cache-size-one probe also passed and did not directly observe an eviction event.

The error path in both 1.5.0 and 1.5.9 is specific: `LocalHnswSegmentReaderError::UninitializedSegment` formats as “Nothing found on disk”; `LocalSegmentManagerError` prefixes “Error creating hnsw segment reader”. Thus the message can mean an absent segment directory, absent `index_metadata.pickle`, or an empty `id_to_label` mapping. By contrast, a present but unreadable pickle and a nonempty mapping whose native index fails to load take distinct error variants. Seeing native HNSW files in a post-failure inventory alone would not rule out the metadata branches.

Current `main` additionally checks the SQLite sequence when the metadata file is missing and validates the persisted checkpoint and native files. That newer source does not retroactively establish which condition existed in the 1.5.0 test failures.

[Chroma issue #7946](https://github.com/chroma-core/chroma/issues/7946) remains open as of this investigation. It reports the same reader error on Chroma 1.5.9, Python 3.11.17, Linux x86-64 under QEMU on Apple Silicon, with an explicitly forced cache size of one. The report describes an intermittent failure after adding a second collection, while querying the first. Its latest discussion (2026-10-27) points out that missing or empty `index_metadata.pickle` state can also yield this message and notes that current `main` has additional checks and live-index reuse. The reporter's later reproductions did not recur consistently. This is a useful lead, not a matching reproduction: this repository runs Chroma 1.5.0 on native 64-bit Windows with observed cache value 102, and its actual failures lack corresponding snapshots.

The project store creates a `PersistentClient` under a plan-owned temporary/persistent index path, maintains separate text and image collections with cosine distance, and delegates vector queries through `collection.query()`. The two affected tests use synthetic temporary indexes; no evidence shows they force eviction or launch concurrent work against the same segment. The plugin and synthetic harness have not observed eviction in this environment.

## Assessment and evidence needed

**Diagnosis: supported but unconfirmed.** Upstream source changes make cache eviction, concurrent cache misses, native index lifetime, and file-handle lifecycle credible areas to investigate. The exact message also has several on-disk initialization causes. None is established for this repository.

No project code or dependency change is warranted now. Revisit if a failing run captures, for the actual temporary segment, the metadata pickle presence and structural count, native-file inventory, SQLite sequence state, operation order, and cache observation. To attribute the incident to eviction, also obtain direct evidence that the relevant cache entry was evicted before the failing query (or reproduce the same failure deterministically against this installed build). A post-exception snapshot must continue to be treated as post-failure evidence, not as the exact transient state at the throw.

A two-process calibration showed Windows' `Popen.pid` can differ from the interpreter's `os.getpid()`, and the runner retained those as separate observations.

The index was confined to this attempt's unique pytest temporary root; no other matrix attempt ran concurrently. The test itself did not spawn a Chroma child. The reservation state at the exception was not captured; the reservation directory was absent after process exit. The report and index manifest existed in the post-exit fixture, but this attempt did not hash them before the query, so byte-for-byte unchanged status across failure is unknown.

### Post-exit persistence evidence

Only after the pytest owner process exited, the runner captured bounded file metadata and opened SQLite read-only within this attempt's test-owned temporary root. It found two collection rows (`text_vectors`, `image_vectors`, dimension 2), four segment rows (one vector and one metadata segment per collection), two max-sequence rows, and the expected vector-segment UUID directories. They therefore do not distinguish this failure from those successes. No pickle was deserialized. The Rust-backed reader's transient mapping state cannot be inferred from these SQLite rows or native-file presence.

### Query, cache, lease, and process observations

The four diagnostics-enabled original-test attempts all succeeded. Their query order was text #1, image #2, repeated text #3, and repeated text #4. The diagnostic snapshots showed one current Chroma system cached at each checkpoint and the same text fingerprint prefix (`c7bcbc467e3a`); no eviction was observed between checkpoints. The reservation and lease object belonged to the query's current process and thread while open and were absent after wrapper close. The four in-process Python PID/thread pairs were `22548/29544`, `9464/27292`, `21680/13088`, and `29480/13036`. The four instrumented Phase 6.12F runs each executed two text queries in the same evaluation child: ordinal 1 for `generation-failure` and ordinal 2 for the explicit `explicit-recovery` call. Both returned. Per query, the Chroma system was cached for the same path, and the writer reservation was owned by the current process/thread during store use. The child PID/thread pairs were `2904/13680`, `30104/31096`, `16920/4952`, and `25636/25752`. This confirms that the recovery path reopens the same fingerprint after the first wrapper closes within that child; it does not show that this lifecycle caused or prevents the original failure.

The four cold retrieval runs used a builder process that exited before the retrieval child started. Each retrieval child observed zero cached Chroma systems before its first open, then successfully queried text ordinal 1 and image ordinal 2 with one system cached and an active same-thread lease. The query-child PID/thread pairs were `28748/2964`, `764/27036`, `20580/13088`, and `22648/28340`. For the instrumented pytest attempts, the Windows command-launch PID differed from the in-test `os.getpid()` and lease owner PID. The launch PID and in-process PID are retained separately; their launcher relationship was not further investigated. Child scripts' own completion records and the orchestrator's bounded waits all showed process exit. ### Hypothesis assessment

- **Chroma cached-system lifecycle:** The controlled failure followed a same-process wrapper close/reopen, and all enabled controls observed a cached system. The original Phase 6.12F failure occurred in a fresh evaluation child on its first retrieval, so same-process wrapper close/reopen is not necessary for the incident. No cache eviction was observed; point samples cannot exclude an unobserved transition. The data does not establish cache behavior as cause, necessary condition, or sufficient condition.
- **Persisted segment initialization:** The failure-time segment metadata and native files were not captured because the occurrence was in the diagnostics-disabled scenario. Post-exit SQLite and file evidence showed expected collection/segment rows and native files, with the same absent pickle and zero-byte link-list files seen in passing controls. This does not establish that the state was complete at the instant of failure and does not select among Chroma 1.5.0's error branches.
- **Timing or cross-test interaction:** The original test failed in a fresh isolated pytest process, so prior full-suite test order is not necessary to reproduce it. The matrix was sequential and used a unique temporary root per attempt; no concurrent same-index matrix process was present. Full-suite scheduling could still change the intermittent rate, but this experiment did not demonstrate such an effect.
- **Instrumentation correlation:** The uninstrumented scenario had one pass followed by one failure; the instrumented scenario had four passes. This small split is not causal evidence. The observer adds checkpoints and filesystem stats and may alter timing. It neither suppressed the exception nor retried queries.
- **Phase 6.12F recovery sequence and process lifetime:** Four recovery smokes passed, with the initial generation-failure evaluation and explicit recovery both querying successfully. Four cold-process retrieval smokes also passed. These results do not reproduce the original Phase 6.12F failure and do not establish a process-boundary fix.

### Decision and retained evidence

**Decision: Failure captured, cause unknown. Phase 6.12F remains blocked.** The controlled occurrence confirms the intermittent error can happen in a fresh standalone run of the original retrieval test without diagnostic instrumentation. It does not establish why. Absence of another occurrence in the enabled/recovery/cold runs does not establish resolution. No deterministic reproducer, cache eviction, missing segment directory at failure, empty mapping, or native-file load failure was observed directly.

No production code, Chroma version, cache setting, retrieval behavior, or evaluation behavior changed. The only local code changes add opt-in test diagnostics and query checkpoints to the diagnostic plugin and Phase 6.12E retrieval smoke; the Phase 6.12F smoke records its query observations in temporary per-attempt output. The original Phase 6.12F untracked files and earlier failed-run directory remain preserved. The controlled matrix evidence is under a unique `%TEMP%` directory; each attempt has its process log, summary, traces/results, and test-owned post-exit snapshots. These temporary paths are deliberately not embedded in this committed incident history.

The historical upstream issue #7946 remains only a related lead under a different Chroma release and environment. The artifact-publisher pre-publication `ArtifactIntegrityError` remains separately unresolved. The full-suite failure count above has not been replaced by these bounded diagnostic passes. No workaround, retry, repair, cache adjustment, dependency change, or risk-acceptance decision is proposed here. Further work requires either a captured failure with failure-time segment identity evidence or a separately approved residual-risk policy; until then, Phase 6.12F remains a release blocker.

## Phase 6.12 minimal-observer experiment plan (2026-11-01)

The next controlled comparison is capped at **eight fresh Python processes**: at most four runs of the original retrieval test with diagnostics off, then at most four runs with the plugin's `minimal` mode. Runs are sequential, each gets a unique attempt ID, a unique pytest `--basetemp`, and isolated Chroma storage. Stop each scenario at its first HNSW failure after evidence capture. Do not extend the budget to seek a failure or a pass. The prior 14-attempt detailed matrix remains separate evidence and is not combined with these counts.

`off` means the pytest diagnostic plugin is not loaded, so it does not replace `ChromaVectorStore._query`. The plugin also accepts an explicit `off` mode for a hook-level no-patch check. `minimal` replaces only `_query` during the named target test. Before each query it appends one bounded event to a 16-entry in-memory ring: ordinal, modality, process/thread IDs, collection name/ID, fingerprint prefix, operation, and monotonic timestamp. Successful queries cause no filesystem walk, cache or lease inspection, JSON serialization, or diagnostic file write; their event buffer is discarded when the test ends. The controlled parent separately records the child's actual `os.getpid()` from a PID file written before `pytest.main()`, its exit status, and the attempt directory.

Only a matching HNSW exception triggers failure-time callback work. The hook retains the original traceback, marks the current ring event as failed, then validates that the storage and index roots resolve beneath the target test's `tmp_path`. For a verified temporary store it captures the collection identity, a point-in-time cache and lease observation, and bounded stat-only Chroma file metadata after the exception. It writes this evidence before the normal retrieval `finally` closes the store, then re-raises the original exception. This is an observation after Chroma raised; it is not an atomic view of Rust state at the instant of failure. SQLite mapping is deferred until the owner process exits; pickle files are never deserialized.

The failure-time event supplies the collection UUID where minimal instrumentation captures a failure. A separate post-exit read-only SQLite inspection may map that collection to its vector-segment UUID and compare the UUID with the segment directory. Such a mapping identifies persisted relationships after process exit only; it cannot establish which Rust reader or mapping existed during the failed query. If no failure occurs in the new matrix, it will provide no new failure-adjacent segment evidence and will be reported as inconclusive.

The two scenarios and their maximum four attempts each were fixed before execution. The first attempt will start only after diagnostic unit tests and compilation pass. Stop the entire experiment if an attempt's evidence ownership or process cleanup cannot be established. No full-suite run is planned: the retained **792 passed, 17 skipped, 1 failed** gate remains failed and relevant.
