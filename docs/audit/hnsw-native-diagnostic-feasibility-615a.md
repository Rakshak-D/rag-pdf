## Source-attribution correction — 2026-11-03

The report was first published in commit `c00a2b1bd9e1947e0dd8185dd52402a27eb301a2` with an incorrect production-path attribution: it described `rust/frontend/src/impls/in_memory_frontend.rs` as building the production KNN plan and delegating to the local executor. That module uses `TestReferenceSegment` and calls its `reference_impl.knn()`; it is not the production frontend selected by the embedded Python binding.

The verified pinned-source path is `Bindings::query()` → the `Frontend` alias (`ServiceBasedFrontend`) → `ServiceBasedFrontend::retryable_query()` constructing the `Knn` plan and calling its configured executor → `LocalExecutor::knn()` → `LocalSegmentManager::get_hnsw_reader()` → `LocalHnswSegmentReader::from_segment()` on a cache miss. The binding config selects `ExecutorConfig::Local`. The corrected source table and links below replace the erroneous attribution.

This corrects source provenance; it adds no runtime observation and does not change the recorded HNSW outcomes. The native-diagnostic feasibility classification remains defensible: the corrected production path still reaches the three source-level `UninitializedSegment` branches, while the inspected embedded Python path does not expose a branch-specific native event. The installed extension's exact source-build identity remains unverified.

## Decision

The current supported Python `PersistentClient`/Rust-bindings path does not expose enough native logging or tracing to identify which `UninitializedSegment` branch produced the HNSW reader error. The exact Chroma 1.5.0 source has three conditions that format to the same `Nothing found on disk` message, and the reader error is converted to Python `InternalError` using its display text. No branch-specific event is emitted at those conditions. `RUST_LOG` is only an `EnvFilter` input when a Rust tracing subscriber has been initialized; the embedded Python binding neither exposes that configuration nor initializes the subscriber in its binding construction path.

Obtaining the branch at failure time therefore needs a separately approved, disposable instrumented native build or an equivalent debugger setup with exact symbols. The least intrusive proposed build would attach a branch code and segment UUID to the existing native error at the branch site, preserving the `InternalError` class and avoiding a new global tracing subscriber. No build, installation, HNSW query, or mitigation was performed here.

This is a diagnostic-feasibility conclusion, not a root-cause conclusion. The HNSW incident remains unresolved.

## Python-to-native query path

The observed application call path is:

```text
retrieve_semantic()
  → ChromaVectorStore.query_text()
  → ChromaVectorStore._query()
  → public Collection.query()
  → installed RustBindingsAPI._query()
  → chromadb_rust_bindings.Bindings.query()
  → Frontend = ServiceBasedFrontend
  → ServiceBasedFrontend KNN plan construction
  → configured LocalExecutor
  → LocalSegmentManager.get_hnsw_reader()
  → LocalHnswSegmentReader::from_segment() on a cache miss
```

The installed Python adapter's `_query()` calls `self.bindings.query(...)`; the application wrapper passes a validated embedding and requested result count to the public collection query. The exact earlier traceback identifies the `Collection.query()` / `RustBindingsAPI._query()` boundary and Python wrappers. The reader error itself originates lower in the Rust segment initialization path.

`get_hnsw_reader()` first checks its in-process HNSW pool. A cache hit returns a reader from the cached index and does not call `from_segment()`. On a miss it loads from the persisted segment, then starts and caches the reader. Thus a post-exit file inventory alone cannot prove which reader path the failed request used.

## Native branches sharing the observed message

In the 1.5.0 source, `LocalHnswSegmentReaderError::UninitializedSegment` displays `Nothing found on disk`. For a persistent segment, `from_segment()` returns that same variant in three distinct cases:

| Branch in `LocalHnswSegmentReader::from_segment()` | Input condition | Same displayed inner error? |
|---|---|---|
| Segment-directory check | `persist_root/<segment UUID>` does not exist. | Yes |
| Metadata-file check | Directory exists, but `index_metadata.pickle` does not exist. | Yes |
| Deserialized ID map | Pickle is present/deserializes, but `id_to_label` is empty. | Yes |

`LocalSegmentManagerError::LocalHnswSegmentReaderError` prefixes the variant with `Error creating hnsw segment reader:`. The PyO3 error conversion maps the internal error code to Python `chromadb.errors.InternalError` and exposes the formatted string. The observed complete message therefore points to `UninitializedSegment`, but it does not distinguish these three conditions.

Nearby failures have different text/variants: an unreadable or malformed pickle becomes an open/deserialize error; a nonempty map with HNSW load failure becomes `Error loading hnsw index`; missing HNSW configuration is separate. The writer-side enum also has an `UninitializedSegment` label, but its manager prefix is `Error creating hnsw segment writer`, not the observed reader message.

At the branch, the Rust objects contain the collection, segment UUID, persistence root, dimensionality, and HNSW configuration; the ID-map branch also has the map and its size. The cache manager has the segment UUID and the pool hit/miss result. The current error variant carries none of these details, and the Python exception is only the formatted error chain. The existing path does not report which check failed.

## Existing diagnostic coverage and its limits

The repository's [opt-in pytest diagnostic plugin](../../scripts/diagnose_chroma_hnsw_pytest_plugin.py), [standalone synthetic diagnostic](../../scripts/diagnose_chroma_hnsw.py), and [focused diagnostic tests](../../tests/unit/test_chroma_hnsw_diagnostics.py) provide useful Python and persistence evidence:

| Evidence layer | Available observations | Limits |
|---|---|---|
| Python before/after query | Query ordinal and modality; Python PID/TID; collection name and UUID; index fingerprint prefix; original exception and traceback; bounded recent event ring; temporary-root provenance; wrapper/store lifecycle checkpoints. | Records the Python adapter boundary, not the native segment-reader branch. Python caller thread identity need not identify a Tokio worker executing Rust work. |
| Python cache/lease observations | Installed `hnsw_cache_size`; whether a Python Chroma system appears cached; point-in-time lease object/marker state. | Unsupported read-only internals and point samples; no per-segment HNSW pool hit/miss or eviction history. A sample cannot rule out transitions between checkpoints. |
| Post-exit filesystem/SQLite | After the owning process exits, bounded file inventory and read-only SQLite collection-to-segment mapping in verified test-owned storage. | Not an atomic failure-time view. It cannot recover the Rust reader's transient `id_to_label`, cache entry, or exact branch. The diagnostic avoids querying SQLite while the Chroma owner is live and does not deserialize pickle files. |
| Native failure-time | No branch event, reader state, per-segment cache outcome, or structured Rust error reason is captured. | This is the missing evidence required for branch identity. |

The minimal observer writes failure-only evidence after Chroma raises and then re-raises the original exception. Its snapshot is post-exception (though before control returns to the retrieval wrapper), not an atomic snapshot at the Rust throw. The standalone probe records the cache-size setting and synthetic-store snapshots but cannot force or observe an individual native cache transition. Neither path substitutes for native failure-time state.

The existing failure records demonstrate the practical limitation: the captured 6.12F-R query-1 failure had no diagnostic plugin attached; the later isolated query-1 failure was diagnostics-disabled; post-exit observations mapped the collection to a segment UUID but did not reveal the reader's failure branch. Passing controls with some of the same post-exit file observations further show why those observations are not branch proof.

## Rust logging and tracing assessment

The Chroma 1.5.0 source includes a Rust tracing utility. Its `init_tracer.rs` builds an `EnvFilter` from `RUST_LOG` (or a default filter), and exposes stdout and OpenTelemetry layers plus `init_tracing()`. However, that only works after the global subscriber is installed.

The embedded Python execution path was checked end to end, rather than inferring logging support from one constructor alone:

- The installed 1.5.0 Python [`RustBindingsAPI.start()`](https://github.com/chroma-core/chroma/blob/ad34d58038fc1e9b6cf73bab8e1df4a5e98aaeda/chromadb/api/rust.py#L73-L126) constructs `Bindings` with reset permission, SQLite configuration, persistence path, and HNSW cache size; it has no logging/tracing configuration.
- The called PyO3 [`Bindings::py_new()`](https://github.com/chroma-core/chroma/blob/ad34d58038fc1e9b6cf73bab8e1df4a5e98aaeda/rust/python_bindings/src/bindings.rs#L69-L139) creates the Tokio runtime and configured local frontend but does not call `init_tracing()`.
- The PyO3 [`chromadb_rust_bindings` module](https://github.com/chroma-core/chroma/blob/ad34d58038fc1e9b6cf73bab8e1df4a5e98aaeda/rust/python_bindings/src/lib.rs#L1-L29) exports no tracing initializer; its source leaves “Log config classes” as `TODO`.
- The exact three `UninitializedSegment` branches contain no `tracing`/logging statement or branch-specific span field. Setting `RUST_LOG` alone cannot create a subscriber or an event that the branch does not emit.

`init_tracer.rs` supplies subscriber construction and an `EnvFilter` based on `RUST_LOG`; it does not itself prove the subscriber is initialized in this embedding path. A host could separately install a global subscriber, but the reader branches still emit no branch-identifying event. Python-level Chroma telemetry/OpenTelemetry can describe API operations at configured granularity, but it does not expose the Rust `from_segment()` branch or internal map state. The installed `.pyd` contains strings such as `RUST_LOG`, `Global tracing subscriber set`, and the HNSW error text; those static strings establish neither that a subscriber was initialized by the Python path nor that a failure branch emits a diagnostic event. No supported environment variable or setting was found that would make the current pinned Python binding expose the needed branch.

**Answer:** Failure-time native branch identity is **not feasible through supported diagnostics in the current pinned embedded Chroma environment**.

## Minimum separately approved follow-up

If native branch identity remains necessary, seek approval for a disposable diagnostic build from the exact 1.5.0 source commit, not for a Chroma upgrade. A small source-only instrumentation patch should:

1. Distinguish the three `UninitializedSegment` causes at the exact branch (`segment_dir_absent`, `metadata_pickle_absent`, or `id_to_label_empty`).
2. Attach the branch code and segment UUID to the existing error while preserving its internal error code, Python `InternalError` class, original traceback, and no-retry behavior. Include collection UUID if safely available. Do not record query embeddings, record IDs/documents, pickle contents, or unrestricted absolute paths.
3. Use the already captured Python query ordinal/modality and a single sequential query in the child to correlate the exception. If that does not uniquely correlate the Rust event, a separately reviewed request-correlation field may be needed; do not infer correlation from Python and Rust thread IDs.
4. Avoid a process-global tracing subscriber unless a separate review proves that it cannot conflict with an embedding application's subscriber. Branch-specific error context is preferable to synchronous log I/O because logging can perturb timing.
5. Build outside the repository and outside `rag-env`; record source commit, clean source diff, `Cargo.lock`, Rust/MSVC toolchain, Maturin version, target triple, wheel tag, build logs, and final wheel/extension hashes. Confirm the custom wheel still reports Chroma 1.5.0 and has the expected `cp39-abi3-win_amd64` compatibility before any test execution.

The source uses PyO3's `abi3-py39` feature and the installed wheel advertises `cp39-abi3-win_amd64`, so Python 3.10 is within the declared stable-ABI range. A Windows native build still requires a pinned, compatible Rust/MSVC build toolchain and Windows SDK. The package source declares Maturin as the build backend, and the installed wheel reports Maturin 1.11.5; this audit did not establish a reproducible toolchain or build. A custom binary would require source/build provenance review and artifact verification; it must not be treated as an official Chroma release binary.

If separately approved, cap the first instrumented runtime evaluation at **one** execution of the existing isolated synthetic retrieval test that previously failed at query 1. Use one owned temporary index, no concurrent queries, no retries, no repair, and no cache override. If the query succeeds, the branch remains unobserved and the attempt stops. If instrumentation, binary identity, evidence ownership, or cleanup fails, stop. If a native failure is captured, preserve the original traceback and branch fields, then stop for review rather than continuing a matrix. Any additional attempts require a new explicit decision after reviewing that evidence.
